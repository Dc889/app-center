# 工单验收记录

每次验收生成独立批次文件夹，历史结果不覆盖。启动命令：`npm.cmd run accept:work-orders`。该命令在隔离本地数据和去除产品/服务凭证的子进程中执行检查，不访问正式Dify/RAGFlow，也不把模拟对端标为真实产品。所有时间字段使用UTC，日期面向用户按Asia/Shanghai解释。

## 一个批次包含什么

- report.json / 运行状态.md：逐条命令、起止时间、退出码、运行状态和日志路径；每完成一步立即落盘。
- source-manifest.json：本轮开始时所有受Git管理或未忽略源码的SHA256；另记Git提交、工作区是否有修改。源码改动后复验必须记录新摘要，不能把旧结果套到新代码。
- live-evidence.json：隔离本地实际服务的能力查询快照、Skill执行/结果ID及文件摘要、EVT历史与资源执行数量、重启结果；不保存服务令牌、会话Cookie或产品密钥。
- 逐步骤.log：完整原始断言和错误。首批失败不得删除，修复后用独立复验记录关联原问题。
- 工单验收台账.md / work-orders.json：人工结合总设计及执行路由核对27工单和分支，引用本批次证据；测试通过不自动勾整单。
- 缺陷与阻塞.md：发现的问题、能力缺口、影响工单、负责人角色、修复及复验状态。

## 结论口径

1. 管理端场景通过：页面/权限/状态机/冻结输入/回写通过隔离或模拟对端用例；不说明产品已执行。
2. 本地真实链路部分通过：使用项目真实服务和本地仓库完成的路径，保留单号、结果、摘要与重启证据；不等于全部分支或生产部署通过。
3. 失败：实际断言不符合预期，原始日志必须保留。
4. 能力阻塞：目标动作缺处理器、不完整或目标部署未核验，不能伪造执行成功。
5. 整单通过：管理端、适用实现分支、权限、持久化、产品副作用、错误恢复和C01–C14适用场景均有对应范围的证据；真实部署范围明确后才能计数。

模块描述符登记和部署核验证据分开检查。GET /capabilities的unsupported/unverified/verified只决定能力条件；verified也不能替代具体工单的业务结果验收。EVT-01直接执行动作为空，人工闭环与系统告警来源、关联业务处置分别核对。

## 必查门槛

所有工单核对申请/预检/补正/撤回、本人和组织权限、审批前零副作用、获准字段与版本冻结、幂等及并发、接单后断线、失败/重试/终止、原ID查证、重启、结果确认与角色可见性。每个动作的下游成功判据取能力组件开发§7，业务分支取总设计附录A，不能仅凭动作名称代表验完。

批次原始证据与最终人工台账共同使用；超时或进程中断保留已落盘结果，恢复前核对具体运行进程，不能仅看到running字样就重复启动。

复验命令：`npm.cmd run accept:work-orders -- --retest <首批ID>`。当前复验选择原失败脚本、智能体模块页面和公共草稿/检查页面，另完整重跑构建/边界/lint/接口与本地真实链路。复验报告写明retestOf与实际执行范围，不能声称所有页面在修复版本上都重跑。当前范围针对本轮AG-03/AG-05两项修改；其他模块的后续缺陷应调整影响分析后选择相应脚本。
