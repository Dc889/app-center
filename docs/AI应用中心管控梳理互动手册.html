模块 01 · 知识库管控

一、知识库（KB）是怎么管起来的？

一句话打通：个人在 Dify 里自己建知识库、传文档、自己用，完全不管；只有当你打算把知识库共享给别人 / 上架知识库仓库时，才必须过「敏感词全文扫描 + 运营审批」。

管控边界：什么管、什么不管？

放开不管（不打扰日常干活）

  • 在自己 Dify 工作区新建知识库（权限 only_me）
  • 个人上传文档、切片、调试检索
  • 自己名下草稿智能体挂载自己的知识库

必须走工单严管（对外扩散节点）

  • 上架共享（KB-02）：扫描全文敏感词 + 划定开放组织边界
  • 跨人绑定使用（KB-03）：在授权边界内申请使用，带有效期
  • 违规下架/剔除文档（KB-05）：发现涉密立刻止损

最容易卡壳的 3 个问题（点击展开）

卡点 1：用户直接在 Dify 里把知识库权限改成「团队所有人可见」，不走 KB-02 怎么办？
应用中心的 P0 合规对账（在「安全事件」页顶部）会读取 Dify datasets.permission 字段：只要发现权限不是 only_me、又没有已批准的 KB-02 工单，就会立刻检出「未备案共享知识库」，运营一键转 EVT-01 安全事件要求整改或回收权限。
卡点 2：知识库已经审批上架了，用户事后又偷偷往里面传了一份涉密文档怎么办？
KB-02 审批时会锁定当时的文档清单指纹；后续知识库发生新增/修改文档，触发 KB-04 变更复审机制，重新跑敏感词扫描；发现违规由运营通过 KB-05 暂停分享或停用文档。
卡点 3：Dify 跨工作区的知识库，A 租户能直接把库挂到 B 租户画布里吗？
这里要分清底层机制：Dify 原生知识库是按 Workspace 强隔离的。同工作区内可以直接调整权限共享；跨工作区复用时，应用中心负责审批留痕与边界授权，底层若要跨租户直接检索，需通过 RAGFlow 或外部知识库 API 桥接。

模块 02 · MCP 外部工具服务管控

二、MCP 是怎么管起来的？

一句话打通：MCP 本质是外部接口工具（可能泄露内网数据或返回违规内容）。所以先登记测安全再进仓库（MCP-01）→ 审核后自动下发绑定到 Dify 工作区（MCP-02）→ 隐藏真实内网 URL → 发现违规随时解绑隔离（MCP-03）。

最容易卡壳的 3 个问题（点击展开）

卡点 1：MCP-01 上架和 MCP-02 绑定有什么区别？为什么要分两步？
两步分工明确：
• MCP-01 是“进货安检”：把一个外部 MCP 服务测完安全性、确认没问题后放进公司「MCP 仓库」（只需测一次）；
• MCP-02 是“领用安装”：哪个业务工作区要用，就点一下绑定，公开服务免审即办、受限服务审批后，系统自动帮他配进 Dify 工作区，用户不需要知道底层内网地址和 Token。
卡点 2：如果用户自己在 Dify「工具 → MCP」里手填了一个外部 MCP 地址怎么办？
Dify 里的所有 MCP 绑定都会被只读同步回应用中心。P0 合规对账（安全事件页）会自动比对：凡是没有对应 MCP-01/02 审批单的绑定，全部标为「未备案 MCP」，运营可直接转安全事件整改。
卡点 3：某个 MCP 突然出漏洞或返回敏感信息，怎么紧急止损？
运维发起 MCP-03（处置类型可选：单工作区解绑 / 目录隔离 / 目录下架），审批通过后直接调 Dify 接口把该 MCP 从工作区移除，并禁止新用户继续绑定。

模块 03 · 插件（Plugin）管控

三、插件（.difypkg）是怎么管起来的？

一句话打通：插件是直接跑在服务器上的可执行 Python 代码，风险最高。所以必须先上传 .difypkg 代码包做静态安全扫描上架（PLG-01）→ 审核后各工作区从仓库按权限安装（PLG-03）→ 跑起来后监控故障率，异常可禁用与复核恢复（PLG-04）。

最容易卡壳的 3 个问题（点击展开）

卡点 1：Dify 本身有官方插件市场，为什么还要建应用中心的「插件仓库」？
因为内网/政企环境既可能断网无法直连 Dify 官方市场，又严禁未经代码审查的第三方 Python 代码直接跑在核心服务器上。应用中心插件仓库相当于“企业内部白名单应用商店”——经过安全扫描和运营批准的包才能进仓库供全员复用。
卡点 2：如果研发人员直接在 Dify 界面上传了一个 .difypkg 安装，平台知道吗？
知道。应用中心直连 dify_plugin 只读库，实时同步全部租户已装插件；P0 合规对账会自动比对出所有没有 PLG-01/03 审批单的「未备案插件」（当前测试服就实时检出了 33 条），支持一键转安全事件整改。
卡点 3：插件（Plugin）和技能包（Skill）有什么区别？
• 插件（PLG-*）：装在 Dify 服务端运行的代码包（.difypkg），由平台调用 Dify API 直接安装到工作区；
• 技能包（SKL-*）：给研发人员下载到本机/代码工程里使用的资料或技能压缩包（SKL-03 只管受控下载与回执，不装进 Dify 服务端）。

模块 04 · 智能体（Agent / App）管控

四、智能体是怎么管起来的？（把前面三项串起来！）

一句话打通：智能体是最终成品（组合了提示词 + 知识库 + 插件 + MCP + 大模型）。在 Dify 里自己搭草稿不管；一旦要正式发布上架（AG-02），系统会把里面的依赖组件全部拉出来做合规体检；上线后管住访问授权（AG-03）、API 密钥（KEY-01）、模型额度（MOD-01）与私自篡改（P0 对账）。

最容易卡壳的 3 个问题（点击展开）

卡点 1：为什么智能体发布（AG-02）要把知识库、插件、MCP 都串起来审？
因为智能体本身是一个“壳子”，真正的风险藏在它绑定的组件里：如果它绑了一个没审过的知识库或未备案的 MCP，对外发布后就会间接泄露数据。所以 AG-02 会自动抽出它用到的全部组件，列出合规核验卡给运营一眼把关。
卡点 2：智能体审批通过后，研发去 Dify 把提示词改坏了怎么办？
两道防线：
1. 审批期间防调包：提交 AG-02 时锁定 Dify 真实 updated_at 版本快照，审批期间如果改过，下发执行前自动拦截；
2. 上线后防私改：P0 合规对账会持续比对 Dify 应用最近修改时间与审批通过时间，发现晚于审批时间即标出「已发布应用私自变更」，可一键转安全事件。
卡点 3：应用要被其他业务系统通过 API 调用，是怎么管的？
不让用户直接在 Dify 里随便建 Key（私建的会被 P0 对账揪出「未备案密钥」）。规范流程是走 KEY-01 登记调用方名称、CIDR、QPS 与有效期 → 审批通过后由平台调 Dify 生成真实 Key 一次性交付 → 到期前在「账号与集成 → 有效期回收」与「个人中心」提醒，到期或不用走 KEY-02 轮换/吊销。
