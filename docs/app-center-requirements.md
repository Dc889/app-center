- 尽量少改已建子系统。文档写不含子系统底层开发。用户要求能旁路就旁路。

### 冲突

1. **知识库的闸门不同。** 文档的知识库开通审批是：先申请创建，配置名称、用途、权限边界和密级，通过后才允许接入向量知识库构建平台。用户的口径是：知识库已经在 RAGFlow 或 Dify 里建好，再用公开申请工单放进共享知识库仓库。审核主要看文档有没有通过安全审查，自动判断、运维人员确认。一个是建库前放行，一个是建库后公开。
2. **智能体入口不同。** 文档写了两次：广场是统一发现入口，不是唯一使用入口；已发布应用可以走 Web、嵌入页面、API，只要鉴权。用户要求必须先上架到本平台智能体广场，别人才能用，并且不能把做好的 Dify 应用直接分享出去。
3. **本平台做不做自动处置。** 文档的运行监测与智能处置要求自动限流、隔离、暂停、下线。Skill 引用异常告警、插件调用异常告警也要求持续异常时自动禁用或隔离。用户说本平台没有执行模块，批准后的动作交给能力组件；Skill 只做上架审核、下载人和下载次数，不做运行告警。插件告警用户没有定死，倾向看 Dify 插件服务和日志里谁跑得多、谁占内存，而不是按调用失败率自动下线。
4. **检索效果。** 文档要求按运行日志做召回率、命中率、低效知识库建议，运营章还要求周统计、月对比报告。用户说只有 RAGFlow 或 Dify 已经有成熟接口才做，否则拿掉。
5. **知识从哪来。** 文档只写一个向量知识库构建平台。用户同时有 RAGFlow 和 Dify 两套知识库，公开的是其中某一个库，获批后要在 Dify 工作流里使用。文档没有这一条。
6. **插件使用要不要工单。** 文档对插件写的是上架审核、目录和使用统计，没有写「公开插件免申请」。使用申请写在 MCP 上。用户要求：发布者标了公开就不用使用工单；没标公开才要安装工单。

### 文档有、用户没定或没提到

- 密级、组织、业务线、警种、项目组标签，以及检索前权限过滤、脱敏。用户只说权限怎么取还没定。
- 嵌入链路协同。用户表示不理解。文档指的是知识库用的 Embedding 模型，必须和模型中心推理网关是同一条链路。
- 双域（用户域 / 数据域）各一套插件仓库、各一套智能体和知识库。用户没说要两套部署。
- 灰度发布、半年应急桌面推演、三类平台周报月报、Prompt 模板审批、高危工具二次确认。
- 调用要把人员身份传到模型中心推理网关的 `user` 字段，并用 traceId 把智能体、知识库、MCP、模型串起来。用户对智能体追溯的要求是：哪个用户、来源 IP、调用次数、时长、告警。IP 是用户加上的；文档写的是人员和凭证，没有把来源 IP 写成智能体调用的必记字段。

### 用户有、文档没写

- 公开申请工单、使用工单、上架工单这套统一工单，以及批准后交给能力组件。
- 组件写 Dify 数据库。文档只写在已建子系统上做权限配置和联调，没写直接写库。
- 安全审查的自动判断加运维人员确认，以及按文档逐篇看有没有过审。
- 超长文本把构建打坏时要盯着。文档有解析失败率、队列阻塞、存储触顶，没有单独写超长文本。
- 用户口述的构建阶段「现代化」和切片并列。按上下文应理解为向量化。文档写的是切片向量化，没有「现代化」这个阶段名。

### 4.6 账号共用

这不是五个仓库之一，但用户的授权、MCP 配置、追溯都取决于它。

- RAGFlow 0.22.1 可以接外部登录。`api\apps\auth\oidc.py` 是 OIDC 客户端，`api\apps\auth\__init__.py` 支持 `oidc`、`oauth2`、`github`。`api\apps\user_app.py` 有 `/login/channels`。这一段不必改 RAGFlow。
- Dify 1.7.1 和 1.14.0 的控制台 OAuth 只有 GitHub 和 Google（两边的 `api\controllers\console\auth\oauth.py`）。1.14.0 的 `EnterpriseService` 会去请求外部企业服务的 `/sso/workspace/last-update-time`，那不是本地可配置的身份源。
- 因此：民警只登录一次，然后自己打开 Dify 开发页，这两棵社区源码做不到。要做到，Dify 接入同一个身份源是二次开发。
- 本平台代用户调用 Dify API（配 MCP、建外部知识库）可以不改登录代码，但前提是本平台拿得到该 workspace 的身份。这和第 5 节问题 1 是一件事。

### 4.7 文档 2.7–2.9 这一段：文档要什么，用户定了什么

文档没有 2.7 这个编号。下面按「安全事件处置域、跨平台运营域、运营分析域」以及紧挨着的安全保障、调用溯源、运行监测来对照。

**安全事件处置域。** 文档要看板、三级研判、应急动作（凭证吊销、权限冻结、路由隔离、工具下线）、链路回溯、值班日志、策略核查、月复盘、半年桌面推演、审计导出。用户没有把这套值守和推演收进这次范围。用户保留的是：操作都审计；智能体要能看到人、IP、次数、时长和告警。自动下线和自动隔离，用户用「没有执行模块」挡掉了。

**跨平台运营域。** 文档要账号开通审批、角色矩阵、SSO、高权限复核、权限审计、日志导出、集成配置和培训。和用户一致的是 SSO 和审计。用户没提角色矩阵到警种/密级、也没提集成培训。SSO 的产品差距见 4.6：RAGFlow 已有 OIDC，Dify 社区版没有。

**运营分析域。** 文档要统一看板、阈值和基线告警、和模型中心联动、三类平台周报、月报、事件台账。用户没有要求周报月报。和用户相关的是告警：智能体要告警；知识库要看健康和构建失败；插件倾向看进程和内存；Skill 不要告警。这些告警规则产品都没有，是旁路。模型中心事件同步不在这两棵树里。

**调用溯源与运营统计。** 文档要按人、单位、地市汇总，并把登录身份传到模型中心 `user` 字段，用 traceId 串起智能体、知识库、MCP 和模型。用户要的追溯更窄：人、来源 IP、次数、时长、告警。人、次数、时长 Dify 已有。IP 没有。单位和地市要有组织标签，产品账号上没有。traceId 跨到模型中心，这两棵树没有。

**运行监测与智能处置。** 文档把限流、暂停、隔离、下线写成系统自动动作，重大处置可以人工复核。用户把执行从本平台拿掉，改成工单批准后由能力组件去做。这是这一段最大的口径差。能力组件若只调用第 4 节已有的停用、卸载、删除 MCP 接口，就还不必改产品。文档写的「策略引擎自动执行」本身不是现成功能。

**安全保障支撑域。** 文档还要求密级隔离、检索前过滤、脱敏、高危工具二次确认、国密传输。两套产品都没有密级字段，也没有检索时按密级过滤。脱敏和二次确认也没有作为知识库/工具的现成流程。用户这次没有把这些定成要做。若以后要在检索结果里强制按密级过滤，那是改 RAGFlow 或 Dify，旁路工单替代不了。

## 5. 还没定的问题

顺序按依赖排。问题 1 不定，后面的授权、MCP 配置和「哪个用户」都定不了。每个问题都给了推荐。

### 问题 1. 一个民警在本平台、RAGFlow、Dify 里是什么关系？

这决定使用工单通过后，能力组件改的是谁的库、谁的 workspace。

1. 一个身份，三处各有自己的用户。知识库和智能体仍在这个人自己的 RAGFlow 用户、自己的 Dify workspace。工单通过后，旁路服务以这个人的身份调用产品已有 API。
2. 所有人进入同一个 RAGFlow team、同一个 Dify workspace。共享靠产品自带的 `team` 和 `partial_members`。
3. 本平台、RAGFlow、Dify 继续各登各的。工单只是台账，人到两个系统里手工改权限。

推荐第 1 种。文档要求统一入口，用户也要求不要分别登录；同时两边的权限都只在自己的租户或 workspace 里生效，没有跨库的公开仓库。第 2 种会把 `me` / `only_me` 的边界冲掉，也和「不能把做好的应用直接分给同事」相抵。第 3 种和文档、用户都不符。

登录要分开看，不能因为选了第 1 种就当成已经打通：

- RAGFlow 0.22.1 已有 OIDC，接到同一个身份源，不必改 RAGFlow。
- Dify 1.7.1 和 1.14.0 的控制台只有 GitHub 和 Google。民警要亲自打开 Dify 页面做应用，就得给这两版加上同一个身份源。这一处是二次开发，目前看不可避免。
- 在 Dify 登录改完之前，配 MCP、建外部知识库仍可以按「每个民警一个 workspace」来定，由本平台持有该 workspace 的调用身份。不要改成全体挤在一个 workspace。

### 问题 2. 使用工单通过后，获批的人怎样在 Dify 工作流里用到这个知识库？

1. 知识库在 RAGFlow：在获批者的 Dify workspace 建一条外部知识库，指到 RAGFlow 已有的 `POST /dify/retrieval`。Dify 不用改。
2. 知识库本来就在 Dify：只在同一个 workspace 里把 `partial_members` 打开。跨 workspace 则没有现成授权接口。
3. 批准后复制一份数据集到获批者名下。

推荐第 1 种处理 RAGFlow 知识库，第 2 种只处理「本来就在同一个 Dify workspace」的库。复制会造出两份文档和两套审查状态，和「一份公开库」不符。跨 workspace 分享 Dify 原生库如果以后必须做，再单独立项，那会是改 Dify 或接受复制。

### 问题 3. 审核时的权限边界从哪来？

1. 只读产品现成字段：RAGFlow 的 `me|team`，Dify 的 `only_me|all_team_members|partial_members`，再加创建人和租户。
2. 本平台工单里另记组织、密级、业务线。检索仍然走产品原来的权限，不在检索时过滤密级。
3. 检索时就按密级和组织过滤。

推荐第 2 种。第 1 种太粗，满足不了文档里的边界，但可以作为自动判断的输入。第 3 种要改 RAGFlow 和 Dify 的检索，和「尽量不改产品」冲突，这次不定成范围。

### 问题 4. 安全审查结论记在哪里？

1. 本平台自己的审查记录，按文档 ID 记通过或不通过。自动判断，运维人员在工单上确认。RAGFlow / Dify 只提供文档列表和正文。
2. 把结论写回产品，例如 RAGFlow 的 `meta_fields` 或 Dify 文档上的新字段。
3. 不做自动判断，由运维人员打开原文抽检。

推荐第 1 种。两套产品都没有审查状态。写回产品要么占用没有约定的 `meta_fields`，要么改表。抽检则和用户说的自动判断不符。

### 问题 5. 未上架的 Dify 应用，Web 站点和 API 还开不开？

1. 按用户口径：未上架不得对他人开放。Dify 增加发布校验。这是二次开发。
2. 按文档口径：广场只是发现入口，Web、嵌入、API 鉴权后就能用。
3. 人可以进 Dify 开发，但对外站点不开放；别人使用必须走本平台，由本平台记人和 IP。

推荐第 3 种。它同时保住「不能直接把 Dify 应用分享出去」和文档里的鉴权使用，来源 IP 也能记在本平台。第 1 种一定改 Dify。第 2 种和用户口径相反。第 3 种若做不到「用户关不掉、也开不了 Dify 站点」，就退回第 1 种，不要假装广场已经挡住了直接分享。

### 问题 6. 检索效果分析做不做？

1. 拿掉召回率、命中率和低效库报表。
2. 只保留两边已有的命中测试，给运维人员人工点一次。
3. 本平台自建标注集，以后再算召回率。

推荐第 1 种，和第 2 种不冲突：自动报表拿掉；命中测试接口留着，不承诺它是效果分析。第 3 种是新系统，这次不做。

### 问题 7. 嵌入链路协同这次管到哪？

1. 只核对 RAGFlow `embd_id`、Dify 数据集的嵌入模型名称是否在模型中心目录里。对不上就在工单里标出来。
2. 嵌入请求改成必须走模型中心推理网关。
3. 这次不管。

推荐第 1 种。这就是文档那句话里能在现有数据上核对的部分。第 2 种要改两边的嵌入调用，用户也还没理解这条，不宜先改产品。第 3 种会把文档里的跨中心协同直接删掉，没有必要，因为读模型名称不用改代码。

### 问题 8. Skill 仓库是不是本平台上的网盘？

1. 是。本平台保存文件，做上架审核、下载人、下载次数。不接运行，不告警。不改 RAGFlow 和 Dify。
2. 这次不做 Skill。
3. 用 Dify 插件包充当 Skill。

推荐第 1 种。这和用户的理解一致，也和「引用异常告警先不做」一致。插件和 Skill 不要合成一个仓库，文档是两个域，审查对象也不同。

### 问题 9. 插件异常看什么？

1. 只看 plugin daemon 这一个服务是否活着、日志里哪个插件报错、容器内存是否过高。不做按调用失败率自动禁用。
2. 按文档做失败率、超时率，超阈值自动禁用。
3. 两样都做。

推荐第 1 种。Dify 没有按插件的内存和失败率接口；用户的倾向也是看插件服务和日志。自动禁用属于执行，和「本平台不执行」冲突。内存来自容器监控，不是 Dify 业务接口，所以也不要为它改 Dify。

### 问题 10. MCP 批准后，写 Dify 数据库还是调现成接口？

1. 用获批者 workspace 的身份调用 `POST /workspaces/current/tool-provider/mcp`，写入他的可用 MCP。不改表结构。
2. 组件直接写 Dify 的 MCP 表。
3. 给 Dify 加一个管理端批量接口，由系统管理员一次配很多账号。

推荐第 1 种。1.7.1 和 1.14.0 都有这个接口。直接写库会绑死表结构，升级 1.7.1 到 1.14.0 时容易断。第 3 种是二次开发，只有在拿不到用户 workspace 身份时才需要，而那是问题 1 没定好，不是 MCP 本身缺接口。
