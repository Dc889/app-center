## 1. 管理系统交付范围

管理组采用按业务功能模块组织的单体结构（旧目录 `management/web/` 与 `management/api/` 已停用并迁完）：
- `management/modules/<模块>/`：各业务模块独立维护前端页面（`web/`）、后端规则与路由（`server/`）、模块测试（`tests/`）、公开入口（`public.web.ts` / `public.server.mjs`）及职责说明（`README.md`）。
- `management/platform/`：身份、工作流/草稿/类型、上传包、证据附件、文件交付、访问策略与能力客户端等公共基础设施。
- `management/app/`：应用装配壳层（`App.tsx`、`service.mjs`）、前后端模块注册中心（`module-registry.*`）与公共工单引擎。
- `management/shared-ui/`：公共 UI 控件、资源选择器、模块契约类型与基础样式。

跨模块调用边界、注册协议与数据写入归属见[内部跨模块契约](../contracts/management-modules/README.md)及[模块清单](../contracts/management-modules/module-manifest.md)，各目录负责人见[CODEOWNERS](../.github/CODEOWNERS)。

以 SKL-03 为例，页面向管理端提交 `POST /api/tickets`；管理端向能力组件提交 `POST /internal/v1/executions`，按流水取文件，完整发送后提交回执。能力组件反向读取冻结输入时，管理端提供 `GET /internal/v1/approved-inputs/{executionId}`。两次调用的接口提供方不同，分别查阅[能力组件契约](../contracts/capability-api/openapi.yaml)和[管理端回调契约](../contracts/management-api/openapi.json)。

独立开发时设置 `CAPABILITY_URL` 和对应的 `INTERNAL_TOKEN`，运行 `npm run dev` 即可用指定的能力服务或模拟对端验证页面与工单。仅启动管理后端用 `npm run service -- management`。单模块自测用 `npm run test:module -- <模块名>` 和 `npm run test:browser -- <模块名>`；合入前执行 `npm run check`（依次校验模块边界、lint、构建与全量集成测试）。双方联调时从仓库根目录运行 `npm run test:integration`，检查重复下发、回执与重启恢复。

管理后端负责会话、角色、组织、工单类型及版本、申请、系统校验、审批、状态、审计、结果确认和页面接口。前端按钮只提交申请、办理当前节点、查询状态、申请取文件或使用已发布智能体。管理后端统一调用能力组件；页面不直连内网服务。面向页面的路由走管理系统自身的会话鉴权和页面权限，两组开发人员只依赖总设计规定的内网接口。

管理系统保管申请说明、审批意见、密级、业务线和工单附件引用。Skill/插件包流式转交能力组件，不作为管理系统的持久文件；Dify、RAGFlow 和模型中心凭证不进入管理系统。

发布工单类型时，由管理端按总设计正文 §4 检查每条流程分支。管理端本地节点可直接验证；资源执行节点须绑定类型版本、动作和适用实现方式，逐项取得目标部署的核验结果。发布检查返回具体缺失节点及原因。模板停用只影响新申请，既有执行和重试保留原路由。所有工单、页面、监控、告警与反向接口都属于本次交付。

类型复制与启用组织已接管理端页面，接口及边界见[类型版本契约](../contracts/management-api/type-versions.md)。复制已发布/停用版本得到独立新草稿，发布时重新核验新版本能力；组织范围按当前会话统一限制新申请与草稿，不回退旧版本。已有工单保留冻结版本。当前组织值来自现有身份目录，正式组织ID与改名迁移仍待接入。

**接单与交付。** 按总设计 §4.1 领取到具体动作或页面区块。对于执行节点，交给能力组的样例应写明哪个角色在什么状态下办理、每个输入来自哪个已批准字段、用哪个账户及工作区执行。用同一份样例模拟受理、结果未知、明确失败和最终成功，核对页面、工单、审计及实际下发次数。对仅在管理端流转的节点说明何时产生关联单。提测时附工单号、执行 ID、预期与实际节点，能力组可凭这些标识查到同一次调用。

| SKL-03：下载权限及版本校验通过后的即办 | `download`；Skill 目录 ID | `version,sha256` 从选定版本读取 | 等待交付时显示领取入口；交付成功写下载流水号、版本、摘要和 `deliveredAt`。 |
| PLG-03：此行演示安装；公开安装校验通过即办，受限安装批准后执行 | `install`；插件目录 ID | `version,sha256,workspaceId` 为批准包版本、版本指纹和目标 workspace | 成功或失败时分别回写安装结果，区别 `pluginUniqueIdentifier` 与 `details.upstreamTaskId`；无上游任务 ID 单独记录。 |
| MCP-02：本人私有且符合边界即办，其余允许申请的走人工审批 | `bind`；MCP 目录 ID | `workspaceId,startsAt,expiresAt,expectedUrlFingerprint` 必填，`targetAppId` 选填；时间范围来自获批工单，指纹由管理后端的 `/internal/v1/binding-contexts/{resourceId}` 预检取得 | 成功回写 `details.providerId`、`details.workspaceId` 和绑定结果；能力组件给出的 `resultId` 是平台绑定记录。 |
| AG-02：完成业务和安全审批后执行 | `publish`；Dify 应用 ID | `snapshotId,workspaceId,publicationVersionId,expectedRevision,scope,targetOrgs,targetAccounts,boundaryOrgs,usages` 均必填；`expectedRevision` 复制审批快照的 `data.catalogRevision` | 成功后写 `resultId`（仓库发布 ID）、发布版本、`details.revision` 和 `details.publishedAt`。页面重新查生效目录后显示，进入待结果确认。 |

AG-02 在审批前读取 Dify 应用快照，保存工作流快照、依赖与批准状态供运维判断。对风险处置或驳回只写工单和审计，能力组件执行请求只带最终授权范围和快照引用。已选范围与组织边界冲突时不发起执行。

从 `GET /internal/v1/resources/dify_app/{appId}?workspaceId=...` 取得的 `snapshotId` 与 `data.catalogRevision` 必须一起冻结。首次发布的修订号为 0。若 `STALE_SNAPSHOT`，保留失败记录和审批证据，重新取快照并按现有工单流程提交审批；执行工作进程不得替换成最新修订号自动重发。

全部动作的触发条件、对应下游和待核验项见[能力组件开发 §7](能力组件开发.md#7-全部工单的执行路由)。监控告警转单、调度型操作和二次处置沿用原工单类型与节点，每个已获准动作单独记录执行 ID。终态成功的前序动作不能随整单重放。

## 4. 持久化下发和结果回写

| 数据记录 | 最少字段及约束 |
| --- | --- |
| 工单与审批记录 | `ticketNo` 唯一；类型和版本、业务快照、执行代表账户、状态、节点、审批人、审批时间、结果确认与审计引用。用状态条件更新阻止双击或两个经办人重复进入执行。 |
| 执行尝试 | `executionId` 唯一；`ticketNo,nodeInstanceId,action,attemptNo,request,status,lastPolledAt,result`；同工单动作只允许一个活跃尝试。`request` 按总设计存冻结后的正文。 |
| 待投递记录 | 在触发状态流转的同一次数据库事务，写入执行尝试和待投递记录；含执行 ID、投递次数、下次投递时间及最后错误。投递工作进程可在重启后恢复。 |
| 交付记录 | `resultId`、账户、执行 ID、文件版本、摘要和字节数，记录正在发送、中断、待回执和已登记。取文件前先锁定工单及流水，把发送记录持久化；同流水正在发送、待确认或待回执时拒绝发起取消。重启后恢复待回执事件；只有实际完整发送的记录才生成回执。 |

后端对 `POST /internal/v1/executions` 的 202/200 记录受理并持续轮询 `GET /internal/v1/executions/{executionId}`。网络断开或 503 时先查询，查不到才用原 ID 和原正文补投；不新建执行，也不因首次超时将工单标失败。建议首轮 2 秒后查询，退避至最多 30 秒一次；超过运营等待阈值显示「正在查证」及最近更新时间。HTTP 400/401/403 或同 ID 冲突记录接口错误并停止自动重发，由运维修复配置或数据后对账；执行是否已接单无法确定时仍需查询。

管理系统锁定当前执行 ID 并按 `status` 更新工单，只由后端写入。过期轮询响应、重复终态或旧尝试终态只可记审计，不覆盖新的状态。

| 能力状态 | 工单表现 |
| --- | --- |
| `queued/running/reconciling` | 执行中；正在查证时单独提示。 |
| `awaiting_delivery` | 执行中，给流水所属账户显示下载入口。 |
| `succeeded` | 落本次节点结果。有后续处置、观察或复核时进入对应节点；其余即办完成，人工单按附录进入待结果确认或该类型规定的下一状态。 |
| `failed` | 执行失败，记错误码与安全错误信息；角色有权限且 `retryable=true` 才允许在原工单建新尝试，生成新执行 ID。 |
| `cancelled` | 已终止。取消请求获得 409 时保留真实执行状态，按原权限处理。 |

业务工单的重试与取消由运维人员处理，账号类配置工单由系统管理员处理。申请人确认结果与执行回写分开记录。用户界面按原业务权限隐藏工单号、调用人和失败明细等受限字段；执行记录和安全错误保留在管理后端及有权限的运维视图。

工单已执行失败时，经办人点“终止工单”只执行管理库条件更新，保留原执行 `failed`、`failureCode`、`details`；已终止后再次点击返回当前状态。条件检查与“重试并新建执行”共用同一工单锁或版本条件。一旦新尝试已创建，沿用旧工单版本的终止请求返回冲突。只有对活动执行点“取消执行”才调用能力组件的 `/cancel`。详见总设计 C01。

## 5. 目录、下载、运行和监控

执行响应现在统一由runtime/execution-state.mjs校验，详见[严格响应契约](../contracts/capability-api/execution-response.md)。所有台账和回执/取消都要求完整原executionId/ticketNo/时间/状态及结果，不兼容缺ID。合法响应仍须通过原业务成功判据；下载无本地发送证明不能完成，同流水元数据不得改变。协议错误不落原始正文，文件会停止自动轮询，运维可从Skill文件执行待办只读查证原执行，修复后恢复；不新建执行、不取消或提交回执。

**版本与工作区选择。** 展开 Skill 迭代记录时调用 `GET /internal/v1/catalog/skill/{resourceId}/versions`，显示日期、变更说明和能否继续下载。选择器保留 `downloadable=true` 项；提交时按选中项复制 `version,sha256`，服务端再次核验。插件/MCP 列表先选 workspace 再显示已装或已绑定状态；无选择时显示“选择工作区查看”，不得把 null 显示成“未安装”。切换 workspace 时清理旧分页和缓存，丢弃之前请求的迟到响应。

- **目录**：管理后端基于会话构造 `X-Account/X-Org/X-Role`，使用能力组件提供的分页、搜索和授权条目。运维和管理员的统计遵循详细设计，用户侧不要用未过滤总量、搜索或错误信息泄露范围外条目。即办/审批按钮依据目录资格和管理工单规则共同判断；不能仅凭页面按钮授权。
- **Skill 交付**：用户从本人工单或仓库下载入口取得流水。管理后端校验会话与工单归属，以当前会话身份读取 `GET /internal/v1/downloads/{resultId}`，转发长度、类型及附件名，边发送边核对摘要。响应已完整发送才持久登记回执，然后异步或同步提交 `PUT /internal/v1/downloads/{resultId}/receipt`。中断则不报成功，提示原流水重取。终态由能力组件回执结果或后续执行查询回写；同一流水只记一次。
- **已发布智能体**：运行/嵌入由管理端登录鉴权后转发 `/agents/{resourceId}/runs`；来源 IP 从可信入口取。访问 API 只依详细设计展示获授权的部署地址和登记信息。运行的流及引用按当前用户权限返回，Dify 凭证不交给浏览器。
- **监控**：按详细设计十页渲染。服务监控读取本机 Docker 中的 Dify 与 RAGFlow 容器；确认不可用时创建 SVC-01 并自动审批后只重启该容器。读不到 Docker 时显示未采集。待办、审批与账号类访问权限来自管理库；下游健康、调用趋势、技术日志和 Skill 交付由能力组件 `/observations` 返回。用能力组件提供的事件 ID 去重，按事件时间统计，无来源用「未采集」，已采集无记录计 0，陈旧数据标最近采集时间。告警规则和转单以详细设计 §9 为准，按规则、对象、窗口证据去重。

管理后端实现总设计 §2.3 的 `POST /internal/v1/delivery-checks/{resultId}/close` 供能力组件查证。控制领取、终止、状态检查的写入共享同一流水锁；封住新领取后，如有已确认交付就持久补投回执，原传输仍在进行或状态不明则回复冲突。已知未发送完的中断记录单独保留。在首次成功回执上附带从可信入口记录的 `X-Source-IP`，不可得时省略。管理人员在失败工单上执行“终止工单”走 §4 的本地转换。

上述关闭回调及运维 `POST /api/tickets/{ticketNo}/cancel` 现已有管理端实现，见[交付关闭与取消契约](../contracts/management-api/delivery-close.md)。发送前中断、发出后未知与完整发送分别保留；在途/未知/待回执不能按未发送取消。原ID查询/取消、丢失响应重启恢复、当前运维权限及审计已接，同机双实例事务互斥已验。用户与管理员不能代办业务取消，封存或取消查证期间不再展示领取入口。真实组件cancel和仓库终结未实现，501/404不伪造已终止；跨主机互斥与未知证据恢复领取仍待完成。

监控请求由管理后端按页面固定 `view` 和 `source`，浏览器参数不能扩大范围。能力组件筛选技术事件，管理后端独立筛选本地工单、审计及关联号，然后再合并。审计导出、总数和下一页都从相同的授权结果生成；用总设计 C06 检查分页边界。Skill 的业务统计采用总设计 §2.3 的结算表，传输诊断只用于排障；工单在 `failed` 后本地终止不重复生成下载失败。

## 7. 从办理节点到执行结果

管理后端按[全部工单执行路由](能力组件开发.md#7-全部工单的执行路由)登记类型版本、操作分支、触发节点和资源定位。26 种工单按分支对应 33 个可下发动作，EVT-01 由本系统记录研判、关联处置和复核。举例：收到插件容器内存告警只开事件；插件调用失败率或超时率达到附录 A §9 的定向禁用条件，才触发 PLG-04。页面按钮、定时任务和人工办理走同一个节点处理入口。

| 管理端节点 | 持久化和下发条件 | 收到结果后 |
| --- | --- | --- |
| 草稿、校验、审批、待补正 | 管理库保存业务字段、附件引用、审批与快照。对话草稿经本人提交，审批前获取可信资源 ID、指纹和范围。 | 按附录节点推进。字段或授权对象变化，旧批准不能用于新的执行输入。 |
| 即办校验通过、人工批准或规则动作到期 | 同事务写节点实例、尝试、获准输入和待投递记录。以节点实例和尝试号唯一去重。系统动作保存来源证据及目标授权，不使用触发人的会话。约定生效时间尚未到时，到点重新检查对象状态。 | 保持可恢复的待执行或执行中状态。调度重启后仍使用原冻结输入和 ID。 |
| 有资源副作用的办理节点 | 四条详细样例用 §3 正文，其余取获准分支生成 `decisionRef`。管理端供能力服务精确读取 `GET /internal/v1/approved-inputs/{executionId}`；200 的字段、基本类型和条件见能力文档 §7，未知 ID 404，跨分区拒绝。专用动作如 AG-02 也可凭同一执行 ID 读取获准的 `fields.policyRef`。同一 ID 始终读同一批准记录。 | 以工单、节点实例和当前执行 ID 作更新条件。写入该动作的结果字段、逐对象结果和下一节点，保留旧尝试供审计。 |
| 有后续处置、观察或复核 | KB-05 的自动暂停与人工处置分别生成节点；PLG-04 定向禁用、恢复、观察后再次禁用分别记录。EVT-01 转出的工单存双向关联和处置目标。 | 单步成功只推进本节点。PLG-04 等待观察期，EVT-01 等待关联结果并按附录分派复核。失败工单的本地终止不能充当处置成功。 |
| 账号变更或改名 | 管理库以人员稳定 ID 锁定变更，保存原名和目标值。供能力组件在外部步骤确认后调用 `PUT /internal/v1/account-changes/{executionId}/commit`，服务鉴权，请求 `{subjectId,ragflowAccountId,difyAccountId,workspaceId}`；值取该次已核验结果，无适用 workspace 时传 null。 | 核对活动执行、批准对象及原映射修订后，原子提交获批角色、组织、业务线、账号状态或新名，使旧权限缓存和会话失效，返回 200 `{subjectId,revision,committedAt}`。重复同内容返回原结果，内容或版本冲突 409。提交前的部分失败保留分步结果和操作限制。 |
| 业务需要重新核对权限 | 实现总设计 §6 的 `POST /internal/v1/policy-decisions`；按分区、稳定人员 ID、当前组织及有效授权计算。只对能力组件开放。 | 规则已撤销或过期返回拒绝；调用失败须让能力组件区分暂不可用。历史工单保留当时审批事实。 |

获准输入由该版本的字段模板生成。数值、时间、列表和资源标识保持原类型。管理后端只投影动作所需的字段，对专用动作补充适用的规则、审批决定或预检证据引用。能力组件的 `result.details.values` 按该动作允许的结果键回填；禁止用返回的任意字段覆盖申请人、审批决定、角色或工单状态。工单类型升级后，待执行和重试仍使用原类型版本。

对于 KB-02/04，管理端提供同一获准输入下的分页 `/documents` 子资源，返回锁定清单上的文档 ID、正文指纹及逐文档结论；字段和权限见能力文档 §8.1。对于 AG-02/04，把运维确认风险的决定和对应快照绑定在同一审批记录上，供能力组件查证。

PLG-03 在附录中明确了公开安装即办和受限安装审批，升级、卸载没有统一的免审条件。两条分支从提交时已发布的工单类型版本读取进入条件和办理节点。若类型版本未配置该分支，管理端显示“此分支尚未配置办理流程”，不按安装的免审规则下发。发布新版本时逐分支模拟，并确认在途旧单仍可按旧版本办理。

当前类型登记的 branchFlows.upgrade、branchFlows.uninstall 分别选择 approval（运维审批）或 instant（权限核验通过后即办）。管理员保存草稿时可暂留空，核验/发布时必须两项均已配置，并验证三个能力动作。批准流程不会被能力端的“免审”权限事实跳过；即办配置也不会越过能力端的拒绝或需审批结论。申请受理后冻结办理方式，已发布配置不可覆盖。复杂多节点设计器仍待实现。

KB-05 已接人工申请与服务告警入口：证据附件使用 POST /api/evidence（二进制、x-filename为UTF-8百分号编码、单份最多10MB），返回evidenceId/sha256/sizeBytes。申请只引用本人附件；附件按摘要保存在管理服务数据目录，未关联工单时其他人不可读，关联后工作人员可在工单查询/办理范围内读取附件。下载使用 /api/evidence/{evidenceId}/file，强制附件与禁缓存。当前仍使用演示角色，正式组织范围与附件审计待补齐。

告警入口及幂等语义见管理端OpenAPI的 /dataset-alerts；自动暂停结果只推进待运维确认，运维选择动作并批准后才产生第二个节点。系统单在运维待办与工作人员查询中显示，人工单仍由申请人确认结果，系统单由运维确认。新节点冻结自己的前置条件，历史节点回调保留历史修订。失败本地终止不能被视为产品已恢复，也不自动恢复分享。

KB-04不接受页面直接新建；内部 /dataset-changes 解析可信所有者并起草到其我的申请，状态待所有者提交。所有者以提交变更审查填写变更原因；运维可退回补正或确认审查，普通批准/驳回入口不适用。确认审查必须逐项绑定新增/修改文档的ID和正文指纹；删除仅列变更明细。运维整体不通过或自动审查不通过会安排KB-05，关联请求写在KB-04记录内，重启补投且双向保存工单号。人工额外否决的新对象另开处置，不能覆盖原单。原暂停目录保持暂停；内容或清单变化要求按新快照复核。结果状态冲突需查证入口尚待补齐，不能仅手工勾完成。

PLG-04只从服务告警入口创建，不出现在手工目录与用户申请中。运维在已禁用待确认节点填写恢复原因、修复说明、修复附件与5–1440分钟观察时长，进入待恢复审核，批准前重读同一实例；管理员只读。恢复API成功进入观察中，观察覆盖完整且到期后才已恢复；数据不足不自动完成。失败观察另开同单禁用节点，重试沿本节点但使用新的执行尝试号；历史获准输入和前置条件仍可精确回调。

定向禁用失败的紧急事件与PLG-04互相关联，升级请求随工单持久保存，事件创建按执行ID去重。事件页面可填写关联处置工单号，后端同时核对旧台账与applications的当前成功动作；恢复后的历史禁用不能作为当前禁用结果通过复核。正式分区授权、紧急告警外部通知、真实监控采样/发送、产品定向禁用/恢复及查证办理仍待联调。

ACC管理页面使用 /api/subjects 选择可信人员，在 /api/account-applications 提交，在 /transition 办理；只有当前以管理员身份登录的人员可调用。角色多选仅影响获批目标，本次登录选择的角色单独校验，不将用户请求提升为其另一管理员身份。组织/业务线来自独立持久目录清单，账号格式为1–100位英数及点/下划线/连字符，旧账户名保留历史归属和唯一性预约。目录目前由可信initialSubjects初始化；无人员同步适配时不能通过表单随意制造目标人员。

AccountDesk提供管理员申请/待办/查询和结果确认，AccountApplication区分开通、停用、组织变更、角色变更及改名。批准前重读两端现状，锁定后到生效时间阻止目标新受限操作；未到生效时间的本地动作可取消，已开始及部分失败不擅自解锁。产品最终回调之前不改本地角色或新名，成功提交后旧会话失效；演示登录可填写改名后的账户并选择其已分配身份。事件归属和另一人复核按稳定人员解析历史名，不能以改名绕过独立复核。正式认证、目录同步、真实组件历史上传/交付映射及产品侧失败查证仍待完成。

历史审计现在在追加时保存org、actorSubjectId、actorRole、actorRevision和actorSource，会话快照在请求间隔离；服务操作与目录登记元数据分别标明来源。已写入的历史前缀不能通过应用持久接口覆盖。旧记录缺少组织时保持null/未采集，不按当前人员资料回填；管理员可查询，运维按已记录的历史组织过滤。审计页可用人员ID检索改名前后记录，导出保留原快照。

上传引用和证据文件以ownerSubjectId识别所有者，账户名只保留历史显示；新上传幂等键按稳定人员/种类/客户端键派生。改名后读取和重试发送当前账户、当前组织、当前角色和服务生成的x-subject-id，不能转发浏览器伪造的身份头。旧引用无人员ID时只按可信历史别名识别同一人员，新增引用不改写原作者名；扫描脱敏仍按当前登录角色处理。真实能力组件须完成对应稳定身份登记适配。

文件工单保存所有者人员ID、提交时身份修订和角色。领取前重新读取当前可见目录及指定版本，必须有download权限且Skill状态为available或规范化approved，版本和摘要同原流水；文件发送前再次检查人员修订、限制和会话是否仍有效。已变化的旧身份不能用来重建丢失/未开始的执行。后台回执带X-Receipt-Mode=server-settlement，只结算服务器已记录完整发送的原流水字节，不开放任何新读取；发送完成日志保留接收人员和当时修订。旧匿名交付在身份变化后须同时有原浏览器会话密钥与当前本人登录，不能凭旧Cookie或账户别名单独领取。当前执行器尚未实现稳定人员映射，真实改名交付仍需联调，不得向其伪造旧账户/组织以绕过校验。

ACC失败与未知结果办理已补管理端入口：管理员以当前revision和办理意见执行“查证原执行”，只GET原executionId，已接单后404停止自动补投且保留限制；缺commit的成功结果仍不能完成。对执行失败且无本地commit的账号单，“核验恢复并解锁”只接受能力端直接返回的封存恢复证明，不接受浏览器证明。审批前产品基线、全部证明字段、时钟偏差、事务及错误语义见[账号恢复契约](../contracts/capability-api/account-recovery.md)。完整证明匹配才释放锁与新名预约、置已终止，保留原失败和恢复审计；缺失基线/未知/部分/过期证明不解锁。80项接口测试和Edge办理通过；真实产品补偿/查证/封存仍待组件实现，其他业务工单查证入口仍待补齐。

业务台账已补“查证原执行”：运维在待办对非终态当前执行填写意见后，以原ID只读查询；管理员只读。结果必须仍满足KB-04/PLG-04原成功判据，密钥沿原白名单脱敏，已确认终态不覆盖。已接单执行404保留阻塞并停止重建；申请人改名/受限不阻止读取原结果，新下发仍需有效身份和下架交付校验。具体API与验收见[业务查证契约](../contracts/management-api/reconciliation.md)。SKL-03交付关闭/取消仍待实现，真实产品查证仍待组件联调。
