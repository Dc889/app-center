# 能力组件开发

本文供执行服务、产品适配器和仓库子系统的开发人员使用。[总设计](总设计.md)定义管理系统可调用的内网契约，[总设计附录 A](总设计.md#business-baseline)收录业务规则和完整表单。[管理系统开发](管理系统开发.md)列出调用方字段来源和回写时机。四个仓库可先用同进程实现或模拟，再按 §4 分别部署。§7 登记全部工单，§2 和 §6 给出四个仓库的联调样例，总设计 §5–6 给出 C01–C14。

## 1. 执行服务和失败恢复

能力组在 `capability/executor/` 实现接单与结果查证，在 `capability/adapters/` 实现产品协议转换。四个自建仓库分别位于 `capability/repositories/skill/`、`plugin/`、`mcp/`、`agent/`（后三项同属 `capability/repositories/`）。执行服务与仓库通过 HTTP 交互，每个服务可分别启动；服务名、端口和模拟对端配置见[开发说明](../README.md)。

管理组调用的执行接口归入 `contracts/capability-api/`，执行服务调用的四库接口归入 `contracts/repository-api/`。新增动作时先核对[动作登记](../contracts/capability-api/actions.json)和 §7 的下游成功判据，再与调用方更新 OpenAPI 及 `tests/integration/`。目前可用 Skill 验证预约、取文件、回执及幂等；插件、MCP 和智能体的当前接通范围见[契约索引](../contracts/README.md)和总设计 §1。

实现总设计 §2。收到命令后校验服务身份和信封，按 `executionId` 原子写入执行记录和任务，保存规范化请求摘要；对象键顺序不影响相等性，数组顺序按约定保留。活跃任务对同一 `ticketNo + action` 串行，第二个不同 ID 的活跃请求返回 409 `ACTIVE_EXECUTION`。持久化执行阶段、请求快照、下游幂等键或任务 ID、已知副作用、最后错误和结果。工作进程崩溃后使用持久状态恢复，外部调用在数据库锁外进行。

经适配器在写入前再核验账号、组织、归属和生效状态；客户端填写的凭证、目标 URL 和 workspace 不作为授权证明。用户态操作按 `account + workspaceId` 查凭证引用及授权关系；账号配置或已授权的自动处置按 §8 使用具备目标权限的服务身份；调用 `workspaces/current` 路由前核验该凭证当前 workspace 与目标一致。不得使用固定全局管理员凭证替代目标账户或自动切换共享会话。发出有副作用的下游调用后，遇到超时或响应丢失先保存 `reconciling`，查下游记录；只有确认没有副作用，或下游明确支持同键幂等，才重发。业务终态由结果查证决定；不把查不到的结果当作失败或成功。没有现成接口或权限能力时写 `UPSTREAM_UNSUPPORTED` 或 `ACCESS_DENIED`。诊断日志按内部执行和下游任务标识关联，禁止记录密钥或带凭证 URL。

取消只允许在确认可阻止后续写入时成功。含下载预约的执行必须与取文件及回执串行处理；若已开始交付且状态未知，拒绝取消并先对账。已确认失败后新开尝试由管理系统决定。若先前执行留下无法回滚的部分副作用，记录到 `details` 并保持不可重试，直到人工查证或补偿。

账户映射按 `product,account,workspaceId` 记录产品账户 ID、显示名称、凭证引用、激活状态和最后核验时间。首批由部署数据预置，后续由既有账号类工单和定期校验维护。`/workspaces?product=dify` 只返回当前请求账户有权使用、且凭证映射已核验的 workspace；没有映射返回空列表，来源不可用返回 503。操作目标仍以执行时核验为准。

## 2. 四个仓库的联调样例

下面的 `payload` 和成功详情是接口约定。除明确选填外，列出的字段必填且拒绝未知键。版本、摘要和 ID 都与总设计同类型。`targetOrgs/targetAccounts/boundaryOrgs/usages` 是去重字符串数组；在生成执行请求前按值排序固定快照。

| `ticketType/action` | `resourceId` | `payload` | 成功写回 |
| --- | --- | --- | --- |
| `SKL-03/download` | 仓库 Skill ID | `version,sha256` | `resultId` 为交付流水号；通用 `version,sha256` 为锁定版本及摘要；`details={deliveredAt}`。 |
| `PLG-03/install` | 内网插件目录 ID | `version,sha256,workspaceId` | `resultId` 为 Dify 包唯一标识；`version,sha256` 来自批准包；`details={pluginUniqueIdentifier,workspaceId,upstreamTaskId}`，上游无任务 ID 时为 null。有任务 ID 的失败也写 `details.upstreamTaskId`。 |
| `MCP-02/bind` | 平台 MCP 目录 ID | `workspaceId,startsAt,expiresAt,expectedUrlFingerprint`，`targetAppId` 选填 | `resultId` 为平台绑定 ID；通用版本、文件摘要为空；`details={providerId,workspaceId,expiresAt}`。 |
| `AG-02/publish` | Dify 应用 ID | `snapshotId,workspaceId,publicationVersionId,expectedRevision,scope,targetOrgs,targetAccounts,boundaryOrgs,usages`；`expectedRevision` 为非负整数 | `resultId` 为平台发布 ID；通用版本为 Dify 发布版本 ID，摘要为空；`details={publishedAt,revision}`，`revision` 为写入后的仓库修订号。 |

### 2.1 Skill 下载

### 2.2 插件安装

1. 查插件仓库批准版本及扫描状态，以 SHA-256 验证包内容，读取目标 workspace 对应的有效登录凭证。安装权限不足、版本撤销或配置缺失时拒绝。
2. 本地 Dify 1.14.0 已核对 `POST /console/api/workspaces/current/plugin/upload/pkg`，`multipart/form-data` 上传 `pkg`，从 JSON 读 `unique_identifier`，并持久化该值。凭证用 `Authorization: Bearer …`，条件以目标部署控制台鉴权为准。
3. 调用 `POST /console/api/workspaces/current/plugin/install/pkg`，JSON `{"plugin_unique_identifiers":["<unique_identifier>"]}`，解析 `{all_installed,task_id}`。接单或 HTTP 2xx 不等于成功。若未确认全部已装，保存任务 ID，轮询 `GET /console/api/workspaces/current/plugin/tasks/{task_id}` 读取 `task`；校验对应唯一标识的任务项。成功前调用 `GET /console/api/workspaces/current/plugin/list?page=1&page_size=20` 等分页读取核对目标 workspace 的插件和版本；任务失败回写失败，任务 ID 丢失或状态不明转查证。
4. 安装端点、任务结构已在仓库源码核对。内网包格式、真实凭证所属和安装权限、目标环境任务与安装列表查询均需实测。旧原型的成功判定不纳入验收。

### 2.3 MCP 绑定

先查 MCP 仓库的正常条目、URL 指纹、模型中心技术注册引用和权限范围。审批前的 `binding-contexts` 结合目录、登录账户、workspace 和边界规则返回资格及指纹，只有管理后端用指纹生成快照。执行时有效期必须满足 `startsAt < expiresAt` 且结束时间尚未过期。尚未到开始时间则在任务里等待，到开始时间再次核验；未登记身份、非本人授权 workspace、目录隔离/下架或地址指纹变化均拒绝。URL 和认证配置来自可信技术目录及凭证引用，工单不传地址。

本地 Dify 1.14.0 有 `POST /console/api/workspaces/current/tool-provider/mcp`。请求包括 `server_url,name,icon,icon_type,server_identifier` 及适配需要的 `icon_background,configuration,headers,authentication`。`server_identifier` 使用可查证的稳定映射，同一 workspace 同一目录条目在重复尝试前先查既有 provider。POST 能返回已创建 provider，即使首次发现工具失败；需另查目标 workspace、provider 状态及可用工具/鉴权，再确认绑定。有效期和目标应用限制须在交付前核验可否真实实施：没有受支持的定时撤销、应用级绑定或对应访问隔离能力时，不把 workspace 级创建当作已满足该工单。能力组件持久化 `bindingId,mcpId,workspaceId,account,providerId,startsAt,expiresAt,state`，记录续期、到期撤销或待查证。凭证作用域、更新/删除接口行为、同 workspace 多账户授权边界、目标应用限制和工具发现需在内网验证。

### 2.4 智能体发布和运行

审批前快照包含 workspace、Dify 应用 ID、模式、发布版本、工作流快照、Web 站点状态、名称、简介、图标、标签，以及知识库、工具、插件、MCP 的依赖和批准状态。执行时按 `snapshotId` 回查，核对当前 Dify 版本与关键依赖；资源变化返回 `STALE_SNAPSHOT`。写入智能体目录后再返回成功，发布时不新建 Dify 应用。

生成快照时按 `(workspaceId,appId)` 从本平台智能体仓库读取并保存 `catalogRevision`。从未发布为 0，已发布、下架或恢复的应用均保留该目录项的递增修订号。执行请求中的 `expectedRevision` 必须等于冻结值。仓库条件写发现修订号已变时，能力组件返回终态 `failed`、`failureCode=STALE_SNAPSHOT`、`retryable=false`。发生响应丢失时先按原幂等键重放并取回已提交的响应，不得把自身成功写入误判成版本冲突。

`scope` 为 `all/orgs/accounts`，对应全网段、指定组织、指定人员。使用 `orgs` 时 `targetOrgs` 非空，使用 `accounts` 时 `targetAccounts` 非空，其余范围数组为空。`boundaryOrgs` 必须和审批通过的组织边界一致；有目标人员时查可信组织映射，按范围和边界交集授权。`usages` 是非空数组，值为 `run/embed/api`。

运行接口接收身份头和受信管理后端设置的 `X-Source-IP`，请求为 `{usage,inputs,query?,conversationId?}`，`usage=run/embed`；应用模式决定内容字段和 Dify 协议。统一返回 SSE，事件 `output` 为 `{runId,delta}`，`done` 为 `{runId,result}`，`error` 为 `{runId,code,message}`；未开始流的调用失败用总设计 HTTP 错误体。会话 ID 只允许同一账户同一应用复用。服务记录实际调用、应用、来源和结果；API 方式继续使用已登记的 Dify API 部署地址。产品读取和运行的版本、凭证和字段映射待部署环境核验，未验证应用模式不打开相应入口。

## 3. 提供给管理系统的数据

目录项目通用字段为 `{resourceId,name,status,actions,data}`；`actions` 为该查询身份当前可见的操作名数组，空数组表示无可用操作。状态和类型字段约定如下。列表和详情沿用总设计分页、范围及身份规则。路径、对象键、凭证、原始 MCP 地址和详细错误只在服务内使用。

| 种类 | `status` | `data` 字段 |
| --- | --- | --- |
| skill | `available/withdrawn` | `version,sha256,sizeBytes,scope,targetOrgs,targetAccounts,author,description,tags,license,deliveredCount`。版本查询返回指定版本。 |
| plugin | `approved/unavailable/withdrawn` | `version,sha256,uniqueIdentifier,publisher,description,permissions,workspaceInstalled,installedCount,installAccess,successfulCallCount`；`installAccess=instant/approval/denied`。 |
| mcp | `active/isolated/withdrawn` | `description,transport,toolNames,boundaryOrgs,externalAllowed,registeredAt,bindingAccess,workspaceBound,successfulCallCount`；`bindingAccess=instant/approval/denied`，`urlFingerprint` 仅运维和管理员可读。无版本字段。 |
| agent | `active/unavailable/withdrawn` | `appId,workspaceId,publicationVersionId,description,icon,tags,scope,targetOrgs,targetAccounts,boundaryOrgs,usages,publishedAt,successfulRunCount`，用户只得到本人实际开放的使用方式。 |

目录的组织和人员列表按角色脱敏，普通用户只获取自己的权限结论；缺失的统计数或 workspace 状态用 null。审批前快照 `data` 结构如下。应用依赖项统一为 `{kind,id,name,version?,approved,externalAllowed}`；涉及安全证据的字段只供有权限的审批视图。时间和版本按租户隔离，过滤权限先于计数。

插件的 `workspaceInstalled` 取已授权 workspace 的已安装清单，MCP 的 `workspaceBound` 取该 workspace 已核验且仍生效的绑定记录。目标明确且可查证时返回布尔值；没有指定或无法查证时返回 null。目录缓存按查询人、组织、角色和 workspace 隔离。动作执行前单独核验真实状态。

| dify_app | `appMode,publicationVersionId,workflowSnapshotId,webSiteEnabled,name,description,icon,tags,dependencies,catalogRevision`。草稿的 `publicationVersionId` 可为 null；`catalogRevision` 为本平台目录修订号，必须有值。 |

## 4. 能力组件到四个自建仓库的契约

### 4.1 公共接口与部署

四个服务各用内网基址和 `/internal/v1` 前缀，以下表格省略前缀。只接受能力组件的服务身份，采用总设计的 HTTPS 双向 TLS、HTTP 错误体和分页约定。服务有 `GET /health/live`（进程存活）与 `GET /health/ready`（依赖可用，未就绪 503），健康正文为 `{status,version}`。各容器配置自己的服务监听地址、存储和证书；数据库或对象存储名称空间各自独立，能力组件不直读其数据表。对象与数据库持久化，发布记录及下载成功流水需跨重启保留。初始部署可用验收种子数据，后续必须走同一写接口。

下面的 JSON 对象字段除标注选填外都必填，时间和标识沿用总设计。写动作携带 `Idempotency-Key`（执行动作使用 `executionId:step`，上传使用同一上传键）；同键同内容返回当前记录，内容冲突 409，不能重复写对象和流水。发布或变更用 `expectedRevision` 做版本条件，首次创建传 0；返回 `revision` 单调递增，冲突 409。列表支持 `q,cursor,limit`。对象读取用字节流和长度/摘要头。审批方式由管理系统决定；仓库只校验记录状态、扫描、条件版本和调用身份。

### 4.2 Skill 仓库

| 路径 | 输入与输出 |
| --- | --- |
| `POST /uploads`；`GET /uploads/{intakeId}` | 与总设计上传和查询结构相同；能力组件额外落审查可见范围。待审对象与已发布对象分离，服务计算摘要和触发扫描；`scan.findings` 项为 `{rule,severity,message}`。 |
| `GET /skills`；`GET /skills/{id}/versions/{version}` | 列表返回当前版本；详情返回 Skill 目录数据加 `resourceId,status,revision`。对象键留仓库内部。 |
| `GET /skills/{id}/versions` | 返回 `{items,nextCursor}`；每项 `{version,sha256,sizeBytes,publishedAt,changedAt,changeNote,historyPolicy,status,scope,targetOrgs,targetAccounts}`。整体下架状态由 `/skills/{id}/status` 的写入记录决定，查询结果另带 `resourceStatus=available/withdrawn`。能力组件结合文件可用性、范围和版本策略计算对外的 `downloadable`；按可见范围取足一页后生成对外游标。 |
| `PUT /skills/{id}/versions/{version}` | 批准或下架指定版本，入参 `{intakeId,metadata,scope,targetOrgs,targetAccounts,status,historyPolicy,expectedRevision}`；`intakeId` 是已扫描的文件引用（纯状态变更时 null）；`metadata={name,author,description,tags,license}`；`historyPolicy=keep_disabled/allow_download`。返回更新后的版本详情。SKL-04 整体下架使用 `PUT /skills/{id}/status`，入参 `{status,expectedRevision}`，原子阻止所有版本新交付。 |
| `POST /deliveries` | 入参 `{executionId,resourceId,version,sha256,account,org}`；预约后返回 `{resultId,version,sha256,filename,contentType,sizeBytes}`。 |
| `GET /deliveries/{resultId}/file` | 仓库校验预约状态和已锁定对象，返回文件字节。能力组件校验管理请求的账户组织和最新授权，转发文件。 |
| `PUT /deliveries/{resultId}/receipt` | 入参 `{sha256,bytesSent}`，按流水唯一记成功，返回 `{resultId,deliveredAt}`。能力组件收到后提交执行终态；重启时重复同一回执，恢复已记流水但执行状态尚未回写的记录。 |
| `POST /deliveries/{resultId}/cancel` | 在能力组件确认没有进行中或已完成的交付后关闭预约，返回 `{resultId,status}`，已交付返回 409。 |

仓库保留实际已交付事件供计数，预约和中断不计成功。已交付流水再次取文件，仅在原版本仍可交付且账户权限仍满足时允许，重复回执返回原时间。能力组件协调预约、取消和执行终态；`GET /deliveries/{resultId}` 返回 `{resultId,status,deliveredAt}`，状态为 `reserved/delivered/cancelled`，未交付的 `deliveredAt` 为 null。下载开始、结束、回执待发等事件由管理后端持久化；存在进行中或待确认的交付时拒绝取消，避免将随后补到的合法回执丢弃。

版本历史写入时，由能力组件在 `PUT /skills/{id}/versions/{version}` 的正文额外传入必填的 `changeNote,ticketNo`，取自已批准工单。仓库首次生效写 `publishedAt`，每次接受新修订写 `changedAt`，同键重放保持时间不变。向能力组件返回的历史行含 `ticketNo`；对外版本历史仅向有权查看该业务工单的运维或管理员返回此字段，普通用户省略。`historyPolicy` 用于历史版本；计算当前版本的资格使用当前版本的上架状态和授权范围。

### 4.3 插件包仓库

| 路径 | 输入与输出 |

## 7. 全部工单的执行路由

本表是管理后端和能力组件共用的动作登记表。27 种工单中，26 种合计 33 个可下发动作名，EVT-01 在管理端流转。§2 的四个动作优先跑端到端测试。其余动作也有确定的下发条件、输入归属及回写判据，可以同时开发。每个部署按动作核验支持情况。未实现或未核验的外部写操作必须返回明确状态，不能从表中有一行就推断已上线。

**请求格式。** §2 的四个动作沿用原有 JSON。下表其他需要下发的动作复用同一执行信封，`payload={"decisionRef":"dec-001"}`。管理后端在下发事务中把执行所需的**获准输入投影**保存为不可变记录。能力组件用自己的服务身份向管理后端调用 `GET /internal/v1/approved-inputs/{executionId}`，得到 `{decisionRef,ticketNo,ticketType,ticketTypeVersion,action,resourceId,account,org,fields,preconditions}`。核对类型版本、动作、工单、资源、目标账户、组织及适用的 decisionRef，找不到或不一致不得调用下游。503 按原执行恢复。凭证、证据原文和审批意见留在各自所有方。该接口仅可用服务身份按执行 ID 精确读取，无跨单列表。

**字段约定。** 表内输入列的业务字段使用附录 A §6 对应字段名作为 `fields` 的 JSON 键，按提交时的类型版本冻结。单选取该单枚举原值；日期时间范围为 `{from,to}`，两端均为 UTC；多选为字符串数组，计数为整数，其他数值按附录字段的业务单位传 JSON 数字，资源/人员选择传 ID，文本为字符串，文本列表为字符串数组，单个日期时间为 UTC RFC 3339 字符串。管理端从模板字段编码映射到本版本约定的 JSON 键，不用页面可变的显示标签生成键。条件字段只在适用分支必填。分支判据取工单审批后的操作类型，不允许 worker 自选。输入列中的 `intakeId` 为上传暂存号，`policyRef` 为总设计 §6 的授权规则引用。结果列的业务回写值置于 `result.details.values`，键与附录字段一致；分步结果用 `details.steps[] = {step,objectId,state,upstreamId,errorCode}`，无上游 ID 时为 null。§2 的四个动作保留其专用结果结构。成功的 `resultId` 为产生或更新的资源/授权/登记 ID，复合作业为可查的执行流水 ID。

`preconditions` 为数组，每项 `{kind,id,revision}`（平台修订号）或 `{kind,id,sha256}`（文件/文档清单/产品配置快照）。资源引用由预检与批准节点保存，首次创建目录项 revision 为 0。变更已有目录、权限或映射必须包含已审批修订号；依赖批量操作使用获批对象清单的不可变快照，执行时不能自行扩大。只读同步可传空数组。条件明确失效时返回 `STALE_SNAPSHOT`，结果不明先查证。附录字段中的密级、业务线在管理系统形成版本化授权规则，组件只用 `policyRef` 经管理系统校验。接口与失效规则见总设计 §6。

RAGFlow 0.22.1 源码已核对只读起点。用目标租户的服务端 API Token 调用 `GET /api/v1/datasets?id={datasetId}` 取知识库，读取 `data` 列表；调用 `GET /api/v1/datasets/{datasetId}/documents` 可分页读取 `data.total` 与 `data.docs`，其中 `run` 可为 `UNSTART/RUNNING/CANCEL/DONE/FAIL`。能力组件应同时检查 HTTP 状态和返回的业务 `code`。这些接口可供审批前快照和采集使用，修改权限、跨系统分享或停用文档须另行对照目标版本核验。

**业务字段回写。** 附录 A §6 中每类工单的执行后只读字段给出键名、枚举和明细表列。管理后端把专用动作的技术结果映射到这些字段，例如 PLG-03 的任务 ID 取 `details.upstreamTaskId`，没有任务 ID 时保留 null；MCP-02 的 provider ID 取 `details.providerId`；AG-02 的上架时间取 `details.publishedAt`。其余动作由组件直接以这些键返回 `details.values`。以 KEY-02 撤销为例，`succeeded` 的 `resultId` 为原登记 ID，`details.values={"旧密钥撤销结果":"成功"}`；轮换成功还必须给出“新Dify密钥ID”和“新密钥后四位”。`reconciling` 时 result 为 null，管理端不能提前写失败或撤销成功。

## 8. 跨模块读写接口

以下为本项目内网接口。除标明由管理后端提供的回调和各仓库的服务接口外，均由能力组件提供。权限、错误体、游标和时间格式沿用总设计 §2。仓库负责持久化领域数据，能力组件负责跨来源核验、筛选和对管理系统返回结果。

### 8.1 从选择资源到冻结输入

管理后端在审批前通过 `GET /internal/v1/execution-contexts/{ticketType}?action=...&resourceId=...&workspaceId=...` 获取动作所需的现状。必填类型、动作、资源 ID；workspace 型操作必填目标 workspace。首次创建使用管理系统预分配的目录 ID，唯一性由仓库的条件创建保证。成功返回 `{snapshotId,ticketType,action,resourceId,capturedAt,fields,preconditions}`。字段按 §7 与附录 A §6 当前分支取值和裁剪，仅返回来自产品、仓库和组件的只读事实，例如文档清单快照、已有批准版本、已装实例、密钥登记 ID、待处置绑定清单。人工决定和角色由管理端填写。快照按分区、业务身份和目标授权隔离；无权读返回 404，依赖未接入 501，暂不可用 503。已有专用接口的文件上传、AG-02 发布和 MCP-02 绑定沿用 §2–3。任选字段在适用且已采到时返回；未采到的必需执行依据不得冒充有效输入。

对目录外的选择项，能力组件提供 `GET /internal/v1/execution-contexts/{ticketType}/candidates?action=...&workspaceId=...&q=...&cursor=...&limit=...`，返回 `{items:[{resourceId,name,source,workspaceId}],nextCursor}`。库、工具、密钥登记、安装实例和绑定按该动作允许的资源种类筛选；首次发布用上传件或产品源 ID 预检，目标目录 ID 在管理端一次分配并随工单保存。人员、组织及审批人候选由管理后端提供。存在专用 `/catalog`、`/resources` 时复用相同的数据和身份判定。

KB-02/04 的人工逐文档结论由管理端保存。组件用 `GET /internal/v1/approved-inputs/{executionId}/documents?cursor=...&limit=...` 向管理端读取 `{snapshotId,items,nextCursor}`，每项 `{documentId,sha256,verdict}`，`verdict=pass/reject/unconfirmed`。仅该次服务身份、工单及批准快照可访问。读完所有页后核对快照 ID、文档数量、清单及正文指纹，任一变化应重新复核。AG-02/04 有依赖告警时，获准输入的 `fields` 附带“告警处理决定”和已批准的快照引用；风险确认只覆盖该份快照。

获准输入中的 `preconditions.kind` 对应实际记录种类，如 `key_registration` 代表本平台密钥登记，`dataset_manifest` 代表文档清单，`skill/plugin/mcp/agent` 代表对应仓库资源。所有资源/快照 ID 均在同一分区、来源和 workspace/tenant 下解释，不能仅按显示名查找。无目录项时首次写预期修订为 0。适配器在最终写入位置复核修订或指纹；产品没有条件写能力时按对象串行，核验实际后置条件，结果未知进入查证。每步记录 `state=pending/succeeded/failed/unknown/compensated`。对步骤已经成功的部分按原 ID 对账。只有所有必需结果明确时才提交整体成功。

### 8.3 监控的清单与事件

| §5 已有来源的补充字段 | `kb_task` 带 `stage,progress,startedAt,endedAt,errorClass`。运行及工具调用保留 `appId,ownerAccount,callerKind,callerAccount,callerOrg,recordNo,timedOut` 以及真实依赖；序号在采集时固定，权限过滤和分页不重排。集成样本带 `sampleKind=probe/api_request` 区分健康检查和真实 API 耗时/成功率。 |

### 8.4 密钥和账号的最后一步

KEY-01 及 KEY-02 轮换产生新密钥时，只有获批申请人在对应执行成功后可通过管理后端请求 `POST /internal/v1/key-registrations/{registrationId}/reveal`。使用会话生成的身份头；返回 200 `{secret}` 并设置 `Cache-Control: no-store`。能力端仅在内存中限时保留产品首次返回的明文。截止时间 `revealExpiresAt` 随登记元数据仅对申请人可见。登记 ID、目标账户和一次性领取状态持久保存。以登记 ID 原子消费领取权后才发送，跨实例也只放行一次。无权或不可见返回 404，已消费、过期或重启后失去明文返回 409 `REVEAL_UNAVAILABLE`。管理端同样禁缓存和记录明文。工单、轮询、日志、历史及审计只保存登记 ID、后四位和领取状态。发送中断记录「领取已消费、展示未确认」，按批准的轮换或撤销流程处理；不得据此自动再建一把钥匙。普通运行使用的服务凭证与这条面向申请人的交付通道分别保管。

ACC-01、ACC-02 的外部变更使用获授权、限产品与分区的配置身份。每步以稳定人员 ID 和产品账户 ID 查证。两端成功后调用管理系统 §7 的 `PUT /internal/v1/account-changes/{executionId}/commit`，按同一请求恢复。收到管理端提交结果并更新能力端身份映射后才返回整体成功。部分成功时保留受影响主体的操作限制；旧名用于查历史，不作为新操作的有效凭据。
